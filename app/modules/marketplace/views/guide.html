Marketplace Developer guide

Build an add-on

An add-on is a folder under addons/<id>/ with an addon.json manifest and the usual controllers/, models/, views/ and routes files. It gets its own menu section, its pages are granted to roles like any other, and an administrator turns it on and off here. Start from the starter add-on below, then read the sections you need.

1. Quick start

Download a working add-on (a Notes page with an SQLite table and one role action) named as you like, and change it into yours.

The id takes lower-case letters, digits and "-", and starts with a letter or digit.
  1. Install it: upload the .zip in Marketplace › Upload add-on, or unzip it into addons/ on the server.
  2. Restart the server (pm2 restart all): routes and manifests are read at start.
  3. Activate it in the Marketplace (the starter is "defaultActive": false).
  4. Grant it: administrators see it at once; give its menu items (and actions) to roles in Roles & Permissions.
  5. Change it: edit the files; restart after changing JavaScript or addon.json. Views (.html) are read on each request.

Prefer to have it written for you? Build it with an AI assistant: describe it and copy a ready prompt.

2. Folder layout

addons/
  ward-notes/                  the folder name is the add-on's id
    addon.json                 manifest (required)
    routes.open.js             routes without sign-in            (optional)
    routes.public.js           signed-in users, no MongoDB needed (optional)
    routes.js                  signed-in users + Centrix database (optional)
    controllers/  ward-notes.controller.js
    models/       notes.model.js
    views/        ward-notes.html
    public/       browser files (scripts, images) you serve yourself
    README.md

Name files <name>.controller.js, <name>.model.js, <name>.service.js, <name>.helper.js, as the app does. An add-on only uses the app's code (app/core/…, and models of app/modules/…); it never changes it, so it can be removed or updated on its own.

4. Routes and access

Each routes file exports an Express router. The app mounts them for every add-on, in this order, and they answer only while the add-on is active:

FileWho reaches itUse it for
routes.open.jsAnyone, no sign-inPublic pages and webhooks. Check access yourself (e.g. a secret token in the link).
routes.public.jsSigned-in users with the permissionPages that use SQLite or other systems, not the Centrix database.
routes.jsSame, and only with a Centrix (MongoDB) connectionPages that read or write Centrix data.

Permissions follow the menu. A request belongs to the menu item whose link is the longest prefix of its path; a role needs that item to open it (administrators have every item). Put every URL of a page under its menu link (/ward-notes, /ward-notes/notes, …), and list other prefixes the add-on owns in paths.

// routes.public.js
const express = require('express');
const asyncHandler = require('../../app/core/http/async.handler');
const { requireAction, requireAdmin } = require('../../app/core/middleware/requireauth.middleware');
const controller = require('./controllers/ward-notes.controller');

const LINK = '/ward-notes';
const router = express.Router();

router.get(LINK, asyncHandler(controller.index));                              // the page
router.get(`${LINK}/notes`, controller.list);                                   // its JSON
router.post(`${LINK}/notes`, requireAction(LINK, 'add'), controller.add);       // an action granted per role
router.get(`${LINK}/settings`, requireAdmin, asyncHandler(controller.settings)); // administrators only
router.use(`${LINK}/assets`, express.static(require('path').join(__dirname, 'public')));

module.exports = router;

5. Controllers and views

A page is rendered with the app's layout (menu, top bar) by res.renderPage(viewFile, locals). Get the view file from the add-on's views/ folder with the view helper:

// controllers/ward-notes.controller.js
const view = require('../../../app/core/view').addon('ward-notes');
const { actionsFor } = require('../../../app/core/permissions');

exports.index = async function (req, res) {
  return res.renderPage(view('ward-notes'), {
    title: 'Ward Notes',                              // the browser tab and breadcrumb
    can: actionsFor(req.user, '/ward-notes')           // { add: true | false } for the page's buttons
  });
};

The view is a Vue 2 template; the locals are its data (read-only: replace a top-level key to change it). There is no build step. <style> and <script> blocks in the view are applied with the page; add Vue options with Page.setup:

<div class="col-12">
  <h1>{{ title }}</h1>
  <button v-if="can.add" class="btn btn-primary" @click="add">Add</button>
  <ul><li v-for="n in notes" :key="n.id">{{ n.text }}</li></ul>
</div>

<script>
  Page.setup({
    data: function () { return { notes: [] }; },
    methods: {
      load: function () { var vm = this; fetch('/ward-notes/notes').then(function (r) { return r.json(); }).then(function (d) { vm.notes = d.notes; }); },
      add: function () { /* POST, then this.load() */ }
    },
    mounted: function () { this.load(); }
  });
</script>

Answer JSON endpoints with { error: '…' } and a 4xx / 5xx status when something fails, and log the details with console.error. Pages already have Vue 2, Bootstrap 4 classes, Font Awesome 5 icons and the app's CSS variables (--primary, --surface, --border, --text, …); Chart.js is at /lib/chart.js/dist/chart.umd.min.js.

6. Data

  • SQLite (data/app.sqlite), always available: const { run, get, all } = require('../../../app/core/config/sqlite'). Create your tables with CREATE TABLE IF NOT EXISTS on first use, and start their names with your id (ward_notes_…). Add columns later with PRAGMA table_info + ALTER TABLE.
  • Settings: one JSON row in app_meta, key <id>.settings.
  • Centrix data (MongoDB): require the app's models, e.g. require('../../../app/modules/patients/models/patient.model'), and put those routes in routes.js.
  • npm packages: list them in "packages". While one is missing the Marketplace shows npm install … and the add-on cannot be activated.
  • Deactivating keeps the add-on's tables and settings; updating it keeps them too.

7. Permissions

  • Pages: each menu item is a permission in Roles & Permissions. New items are granted to no role until an administrator ticks them.
  • Actions ("actions" of a menu item): extra rights inside a page, such as "Add notes". Check them with requireAction(link, key) on the route and actionsFor(req.user, link) for the buttons. When an add-on is first activated, its actions go to the roles that have the page.
  • Administrators only: "adminOnly": true on a menu item, and requireAdmin on its routes.
  • Widgets ("widgets"): parts other pages can show (as Query Studio's Basic Data). Each has its own link /widgets/<id>/<key> and permission, and serves <link>/widget.js.

8. Package and upload

  • Zip the add-on folder (ward-notes/addon.json, …) or its contents (addon.json at the top). One add-on per .zip.
  • Limits: 20 MB zipped, 50 MB and 2,000 files unpacked; plain file names (letters, digits, . _ - @ ( ) + and spaces). No node_modules; no encrypted or ZIP64 archives.
  • Upload it in Marketplace › Upload add-on. You see what it is and what it does (new or update, files, routes, packages, paths shared with other add-ons) before installing.
  • Updating an installed add-on (same id) moves the old folder to data/addon-backups/<id>-<time>; copy it back to roll back.
  • Restart the server after installing or updating. Raise "version" with every release.
Security. An add-on runs inside the app with its full rights: the files, the databases and the network. Only administrators can upload, and only code you trust should be installed. Check input in your routes, and keep open routes (routes.open.js) behind a secret or read-only.
